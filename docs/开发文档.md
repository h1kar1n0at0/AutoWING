# 开发文档

面向本项目开发者的架构说明。

## 项目背景

AutoWING 是《偶像大师 闪耀色彩》(enza 版) 的自动化工具。它通过 CDP 截取游戏画布、OpenCV 模板匹配识别游戏状态、CDP 后台点击模拟操作，实现全自动育成。自动化引擎采用「状态检测 → 策略决策 → 动作执行」分层架构，各季度玩法以独立策略类实现。

## 目标读者

想参与本项目开发的开发者。

读完本文你应当掌握：

- 项目整体架构（Orchestrator / Flow / Strategy 如何协作）
- 核心模块的职责和关系

## 架构说明

### 数据流总览

```
TemplateDetector (状态检测)
        |
        v  每 tick
Orchestrator (主循环, 无调度逻辑)
        |
        +--> Flow (流程状态机) --返回--> Action (动作指令)
        |        |                              |
        |        +--调用--> Strategy (季度策略)  |
        |                                       v
        +----------------------------------> 执行层 (click / wait / navigate)
```

一次典型的育成流程：

```
PRE_TRAINING  → PreTrainingFlow (育成前设置)
TRAINING      → TrainingFlow (育成主循环)
POST_TRAINING → PostTrainingFlow (结算跳过)
```

### 启动与运行时序

```text
run.py
        ├─ 加载 Canvas 校准数据
        ├─ 启动 FlaskServer
        └─ 打开 DesktopWindow / 外部浏览器 / headless 模式

控制面板
        ├─ 检测 Canvas → coord.calibrate()
        ├─ 绑定浏览器窗口
        └─ 启动自动化 → Orchestrator.start()

Orchestrator
        ├─ 检测 GlobalState
        ├─ 创建对应的顶层 Flow
        ├─ 调用 flow.step(ctx)
        ├─ 执行 Flow 返回的 Action
        └─ 根据 ctx.signal 切换 Flow 或停止
```

Canvas 的截图和 CDP 页面交互由 `canvas_session.py` 管理。视觉检测从后台截图缓存读取画面，输出统一使用 1600×902 参考坐标；动作执行层再将参考坐标换算为实际坐标。

### 通知系统

通知是横切关注点，独立放在 `app/notify/`，不得反向依赖 `engine`、`core` 或 `api`。业务模块只创建 `NotificationEvent` 并调用通知服务的 `publish()`，实际 Apprise 发送由后台 daemon worker 完成。

```text
Orchestrator / canvas_session / Flask API
                                                                |
                                                                v  publish(event)
                        NotificationService
                                ├─ NotificationPolicy
                                │    ├─ 最低级别过滤
                                │    ├─ 按 event_type + dedup_key 去重
                                │    └─ 按 event_type 时间窗口限流
                                └─ 有界 Queue → NotificationSender → Apprise
```

`NotificationService` 的主要接口：

```python
start() -> None
publish(event: NotificationEvent) -> bool
reload(config: NotificationConfig) -> None
stop(timeout: float = 2.0) -> None
```

约束如下：

- `publish()` 只做策略判断和非阻塞入队，不执行网络请求；队列满时丢弃新事件并记录日志。
- worker 捕获所有发送异常，只记录事件类型和异常类型，不把异常抛回业务线程。
- 通知级别固定为 `info < warning < error`，默认最低级别为 `warning`。
- 手动测试事件设置 `bypass_level_filter=True`，但仍经过异步队列。
- 去重和限流使用单调时钟；调用方必须提供稳定的 `dedup_key`，避免按 tick 重复通知。
- `runtime.py` 持有应用级唯一服务实例。`FlaskServer` 启动时启动 worker，停止时有限等待 worker 退出。
- `canvas_session` 和 `orchestrator` 使用惰性导入访问 runtime，避免 `app.core`、`app.engine` 初始化时形成循环依赖。

#### 通知配置

通知字段与策略配置一起保存到 `configs/strategy.json`，对应 [config_models.py](../app/engine/config_models.py) 中的 `StrategyConfig`：

| 字段 | 默认值 | 说明 |
|---|---:|---|
| `notifications_enabled` | `false` | 是否启用通知发送 |
| `notification_urls` | `[]` | Apprise URL 列表，后端保存完整值 |
| `notification_min_level` | `warning` | 最低通知级别 |
| `notification_dedup_seconds` | `60` | 相同事件去重窗口 |
| `notification_rate_limit_seconds` | `30` | 同类事件限流窗口 |
| `notification_queue_size` | `100` | 后台队列容量 |

API/UI 不回显完整 URL。`/api/strategy-config` GET 和 POST 响应使用 `mask_notification_url()` 脱敏；用户提交未修改的掩码值时，后端通过 `merge_notification_urls()` 保留配置文件中的完整 URL。日志也不得记录 URL、token 或密码。

控制面板的通知设置位于中间栏两个技能卡片下方。技能学习顺序、主动技能优先级和通知设置三个卡片默认收起；通知卡片提供配置保存和异步测试通知按钮。

#### 事件接入点

| 事件 | 级别 | 接入位置 | 去重语义 |
|---|---|---|---|
| 育成完成 | `info` | `Orchestrator._on_training_run_done()` | 运行编号 |
| 达到目标次数自动停止 | `warning` | `_on_training_run_done()` | 目标次数 |
| `StopSignal` | `warning` | `_handle_signal()` | 停止原因 |
| Flow 异常 | `error` | `_tick()` 的 Flow 异常分支 | Flow 类型 + 异常类型 |
| 循环异常 | `error` | `execute()` 外层异常分支 | 异常类型与时间窗口 |
| 连续 UNKNOWN 超过 10 次 | `warning` | `_tick()` UNKNOWN 分支 | 每次跨越阈值一次 |
| 连续异常超过 30 次自动停止 | `error` | `execute()` | 单次执行一次 |
| CDP 意外断开 | `warning` | `canvas_session._bg_worker()` 的 `finally` | worker 标识 |
| 手动测试 | `info` | `POST /api/notifications/test` | 绕过最低级别过滤 |

通知接入失败不能改变原有停止、重试、Flow 切换或 CDP 清理逻辑。

### 三层状态体系

见 `app/engine/state.py`，按检测优先级从高到低：

- **GlobalState**：大阶段。`PRE_TRAINING` / `TRAINING` / `POST_TRAINING` / `UNKNOWN`
- **SeasonState**：季度。`S1` ~ `S5`，另含 `from_string` / `to_string`
- **PageState**：子页面。`MAIN` / `SKILL_UNLOCK` / `SCHEDULE_SELECT` / `PRE_AUDITION` / `IN_AUDITION` / `POST_AUDITION` / `STORY` / `UNKNOWN`

### Orchestrator 主循环

见 [orchestrator.py](../app/engine/orchestrator.py)，自身不含任何流程逻辑，全部委托给 Flow。每 tick 两条分支：

1. **有活跃 Flow**：调用 `flow.step(ctx)`，返回 Action 则执行，返回 `None` 表示流程自然完成，清空 `_active_flow`。
2. **无活跃 Flow**：`detector.detect_global()` 判定全局状态，映射到对应 Flow：

   | GlobalState | Flow |
   |---|---|
   | `PRE_TRAINING` | `PreTrainingFlow` |
   | `TRAINING` | `TrainingFlow` |
   | `POST_TRAINING` | `PostTrainingFlow` |
   | `UNKNOWN` | 计数并 sleep 0.5s |

**信号机制**：Flow 通过 `ctx.signal` 向 Orchestrator 发送控制信号（见 [flows/base.py](../app/engine/flows/base.py)）：

- `StopSignal(reason=...)` — 停止整个引擎
- `SwitchFlowSignal(target=..., kwargs=...)` — 切换到目标 Flow，target 取值 `pre_training` / `training` / `post_training` / `idle`

**错误处理**：主循环捕获所有异常，连续异常超过 30 次自动停止，每次失败后指数退避 sleep。

**动作执行**：`_execute_action` 按 Action 类型分发到执行层（点击/长按/等待/稳定等待/模板等待/连点/序列/QTE/导航/子任务）。

### Flow 状态机

见 [flows/base.py](../app/engine/flows/base.py)。Flow 是实现 `step(ctx) -> Optional[Action]` 的类：

- `step()` **不阻塞、不直接点击**，只返回 Action 或 None（None = 流程完成）
- 内部自管状态（子状态字段 / 子 Flow 实例）
- 需要切换流程或停止时设置 `ctx.signal`

以 [training.py](../app/engine/flows/training.py) 为例，它内部维护子状态并持有子 Flow 实例：

```
TrainingFlow._sub_state:
  event_skip       # 常态: 高速连点跳过剧情
  main_page        # 路标切入: 一站式检查(季度/技能)与决策
  audition_fight   # 视镜战斗 (AuditionFightFlow)
  audition_result  # 视镜结算 (AuditionResultFlow)
  skill_learn      # 技能学习 (SkillLearnFlow)
  event_skip_final # 最终视镜后的跳过模式
```

**Flow 分两种层级**：

- **顶层 Flow**：由 Orchestrator 根据 GlobalState 直接创建（pre/training/post_training）
- **子 Flow**：被其他 Flow 内部实例化调用（`AuditionFightFlow`、`AuditionResultFlow`、`SkillLearnFlow`），不需要改 Orchestrator

### Strategy 策略层

见 [strategy.py](../app/engine/strategy.py)。每种季度玩法实现一个 `SeasonStrategy` 子类，核心是：

- `season` 属性 — 该策略负责的季度
- `get_action(page, ctx)` — 当前页面下该做什么，返回 Action 或 None（None = 本 tick 无需动作）
- 可选 `get_option_action(opts, ctx)` — 剧情分支选项的决策
- 可选生命周期 hooks：`on_enter_global` / `on_exit_global` / `on_enter_page` / `on_exit_page`
- 可选 `on_error(page, ctx, error)` — 动作出错时的恢复

**调用时机**：在 MAIN 页面时由 `TrainingFlow._call_strategy` 调用。策略决策链见 `TrainingFlow._decision_chain`：

```
季度任务到期(强制视镜) → 约定待履行 → 体力不足(休息) → 正常策略决策
```

**注册**：见 [registry.py](../app/engine/registry.py)，使用装饰器注册，且采用**静态导入**，以保证 PyInstaller 打包后策略不缺失。

**修改边界**：项目目前以维护现有季度策略为主。修改策略时，应优先只调整对应的`strategies/sX_strategy.py`；只有确认问题属于公共流程或公共动作时，才修改 Flow、`action_utils.py` 或核心模块。Strategy 不应绕过 Action 系统执行操作。

### Context 共享上下文

见 [context.py](../app/engine/context.py)。Orchestrator / Flow / Strategy 共享的运行时内存：

- `config` — 策略配置缓存（UI 修改后通过 `reload_config()` 热重载）
- `strategy` — 当前季度策略实例（跨 tick 持久化）
- `season` / `remaining_weeks` / `global_state` — 核心游戏状态
- `season_data` — 跨 tick 任意读写临时标记（如 `forced_action`、`in_multi_step_decision`）
- `signal` — Flow 发往 Orchestrator 的信号
- `record_global_transition` / `record_season_transition` — 状态转换时自动清理旧数据
- `step_produce_page()` / `step_produce_page_limited()` — 浏览器前进/后退的跳刀（带 32 秒窗口内最多 2 次的限流）

### 坐标系统

- 所有逻辑坐标基于参考分辨率 **1600x902**，由 [coord.py](../app/core/coord.py) 自动换算到实际渲染尺寸
- 模板匹配 `find()` 直接读后台线程的缓存快照（约每 0.15s 刷新），坐标输出统一为 1600x902 参考系
- 点击引擎 [clicker.py](../app/core/clicker.py) CDP 优先，失败回退 Win32 `PostMessage`

### 动作系统

- [action.py](../app/engine/action.py)：所有 Action 是 **frozen dataclass（不可变）**，防止 Strategy 通过修改 Action 间接共享状态
- [action_utils.py](../app/engine/action_utils.py)：原子操作工厂，把「决策」翻译成「具体指令」。**策略层只调用原子操作，不直接构造 Action，不硬编码坐标**

分层关系：

```
策略层 (strategies/*.py)     决定"做什么"
原子操作层 (action_utils.py) 封装参数, 生成具体指令
动作定义层 (action.py)       定义 Action 数据结构
执行层 (orchestrator.py)     执行 Action, 实际操作游戏
```

## 维护与排查

### 按现象定位模块

| 现象 | 优先检查位置 |
|---|---|
| 无法连接浏览器或找不到 Canvas | `canvas.py`、`canvas_session.py`、浏览器 CDP 端口 |
| Canvas 检测成功但点击整体偏移 | `coord.py`、Canvas 校准数据、窗口缩放/DPI |
| 页面一直处于 `UNKNOWN` | `detector.py`、`templates.py`、对应 `assets/` 模板 |
| 状态识别正确但选择错误 | 对应 `strategies/sX_strategy.py`、策略配置 |
| 策略返回动作但动作未正确执行 | `action_utils.py`、`action.py`、`orchestrator.py` |
| 页面导航、后退或 QTE 异常 | `canvas_interaction.py`、`clicker.py` |

排查时先判断问题发生在哪一层：**识别错误**、**策略决策错误**、**动作生成错误**还是**动作执行错误**。不要在策略层修复属于模板识别或坐标校准的问题，也不要为了单个季度的特殊情况修改全局 Flow。

### 手动验证流程

项目依赖真实游戏页面、CDP 连接和 Canvas 画面，建议修改后以实际运行观察为主要验证方式：

1. 启动 AutoWING。
2. 启动带 CDP 调试端口的 Chromium 浏览器并进入游戏页面，完成 Canvas 检测和窗口绑定。
3. 确认控制面板中的 Canvas 尺寸、位置和校准状态正确。
4. 启动自动化，观察日志中的全局状态、季度状态和 Flow 切换。
5. 在修改涉及的页面实际运行到对应阶段，确认识别、点击、导航和等待行为。
6. 运行结束后重新启动一次，确认配置和校准数据仍符合预期。

日志位于 `logs/`，控制面板还会通过 SSE 显示运行日志。
